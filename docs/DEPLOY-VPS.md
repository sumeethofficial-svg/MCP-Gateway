# Deploying to a VPS (k3s)

The same chart that runs on your laptop runs here. Only the values differ. The reference deployment is a single AWS EC2 instance running k3s; any Linux VPS works the same way.

## What changes between local and production

`charts/mcp-portal/values-local.yaml` vs `values-prod.yaml` (everything else is `values.yaml`):

| Setting | Local (k3d) | Production (k3s VPS) | Why |
|---|---|---|---|
| `ingress.host` / `shopHost` | `mcp-portal.localtest.me` / `shop.localtest.me` | your real domains, or `mcp.<ip>.sslip.io` / `shop.<ip>.sslip.io` | public DNS |
| `platform.stores.baseDomain` | `stores.localtest.me` | `stores.<your domain>` or `stores.<ip>.sslip.io` | extra stores get `<id>.<baseDomain>` |
| `ingress.scheme`, `ingress.tls.enabled` | `http`, off | `https`, on | TLS via cert-manager (see *No domain* below for an HTTP-only demo) |
| `ingress.annotations` | none | `cert-manager.io/cluster-issuer` | automatic certificates |
| `platform.gateway.cookieSecure` | `false` | `true` | session cookie only over HTTPS |
| `platform.gateway.replicas` | 1 | 2 (+ PodDisruptionBudget) | survive node maintenance / rollouts |
| Admin and WordPress passwords | fixed demo values | **generated**, kept across upgrades | nothing predictable |
| `platform.evil.enabled` | `true` (for the malicious-server demo) | `false` | the fixture is malicious by design |
| `platform.stores.maxPerUser` / `maxTotal` | 2 / 4 | 3 / 8 (the defaults) | a laptop has less memory than a server |
| Images | `mcp-portal-*:dev`, imported into k3d | `ghcr.io/<you>/mcp-portal-*:<version>`, or imported into k3s | a registry the VPS can pull from |
| Storage class, volumes, limits | `local-path`, small | per your provider, larger | real data |

Ingress, storage and secrets in one line each: **ingress** is Traefik (built into k3s) on ports 80/443 with two hosts; **storage** is the k3s `local-path` class unless you set `storageClassName`; **secrets** are generated by Helm on first install, kept on upgrade, and never committed (the LLM key goes in a git-ignored values file).

## 1. Prepare the server

A Linux VPS with 2 vCPU / 4 GB RAM runs the platform and one store. Each extra store requests about 1 GB, so use 8 GB if you want to demo multi-store. On AWS EC2, open **inbound 22, 80 and 443** in the security group; nothing else needs to be reachable.

```bash
curl -sfL https://get.k3s.io | sh -          # includes Traefik and a NetworkPolicy controller
mkdir -p ~/.kube && sudo cp /etc/rancher/k3s/k3s.yaml ~/.kube/config && sudo chown $USER ~/.kube/config
curl -fsSL https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash
```

### With a domain (TLS)

Point two DNS records (A or AAAA) at the server: `mcp-portal.<domain>` and `shop.<domain>` (and a wildcard `*.stores.<domain>` if you will create extra stores). Then:

```bash
helm repo add jetstack https://charts.jetstack.io && helm repo update
helm install cert-manager jetstack/cert-manager -n cert-manager --create-namespace --set crds.enabled=true
kubectl apply -f - <<'YAML'
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata: {name: letsencrypt-prod}
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: you@example.com
    privateKeySecretRef: {name: letsencrypt-prod}
    solvers: [{http01: {ingress: {class: traefik}}}]
YAML
```

### No domain (sslip.io, HTTP only)

`sslip.io` resolves any name that ends in an IP address to that IP, so `mcp.<ip>.sslip.io`, `shop.<ip>.sslip.io` and `<id>.stores.<ip>.sslip.io` all point at the server with no DNS work. This is how the reference deployment is reached. It is plain HTTP, so also set `ingress.scheme=http`, `ingress.tls.enabled=false` and `platform.gateway.cookieSecure=false` (see the values file below), and skip cert-manager. Fine for a demo; use a real domain with TLS for anything with real customers.

## 2. Images

Build in CI or locally and push (replace `ghcr.io/you`):

```bash
make images TAG=1.0.0
for i in gateway dashboard woo-mcp kube-ops-mcp currency-mcp evil-mcp provisioner; do
  docker tag mcp-portal-$i:1.0.0 ghcr.io/you/mcp-portal-$i:1.0.0 && docker push ghcr.io/you/mcp-portal-$i:1.0.0
done
```

(`evil-mcp` is the source folder and image name of the malicious test server; its Kubernetes Service is `malicious-test`. The provisioner image contains the store chart.)

For a private registry add a pull secret and `--set 'image.pullSecrets[0].name=regcred'`. For a single server with no registry: `docker save` the images, copy them over, and `sudo k3s ctr images import -`, then use `image.registry=""`.

## 3. Install

Keep your environment's choices in one small file next to the repo, and **never commit it** (it holds the LLM key; add it to `.gitignore`):

```yaml
# my-values.yaml
ingress: {host: mcp.<ip>.sslip.io, shopHost: shop.<ip>.sslip.io, scheme: http, tls: {enabled: false}}
image: {registry: ghcr.io/you, tag: "1.0.0"}
platform:
  gateway:
    cookieSecure: false          # HTTP-only demo; leave true behind TLS
    bootstrapAdmin: {email: you@example.com}
    llm:
      apiKey: "<provider key>"
      baseUrl: "<provider OpenAI-compatible endpoint>"
      model: "<model>"
  stores: {baseDomain: stores.<ip>.sslip.io}
```

```bash
helm upgrade --install mcp-portal charts/mcp-portal -f charts/mcp-portal/values-prod.yaml -f my-values.yaml \
  --namespace default --wait --wait-for-jobs --timeout 20m
```

Include `-f my-values.yaml` on **every** deploy. Helm resets any value you do not pass again, so an LLM key given once with `--set` is gone after the next upgrade.

The first install takes a few minutes: the setup Job downloads WooCommerce from wordpress.org. Follow it with `kubectl -n store logs job/wordpress-setup -f`. `helm` prints the commands to read the generated admin passwords.

Then `BASE=http://mcp.<ip>.sslip.io ADMIN_PASSWORD=... node scripts/demo-users.mjs` creates the demo admin and member for a recorded demo (skip it for real use and use *Team → Invite* instead).

Check the install: `kubectl get pods -A` (everything Running or Completed), open the dashboard, sign in, and confirm *Servers* shows woo, kube-ops and currency as Connected.

Hardening to apply before real customers: restrict `/wp-admin` and `/wp-login.php` on the shop host to your IPs (a Traefik `ipAllowList` middleware or a firewall rule), turn on TLS, and take a backup (below).

## Upgrades

```bash
git pull && make images TAG=1.1.0   # push as above
# bump image.tag in my-values.yaml, then:
helm upgrade mcp-portal charts/mcp-portal -f charts/mcp-portal/values-prod.yaml -f my-values.yaml \
  --namespace default --wait --wait-for-jobs --timeout 20m
helm history mcp-portal
```

* Gateway and dashboard roll with `maxUnavailable: 0`, so there is no gap. Gateway migrations run at start under a Postgres advisory lock, so two replicas starting together are safe. Migrations are additive; destructive changes ship in two releases.
* Passwords and keys are **kept** (read back with `lookup`), so an upgrade never rotates a credential under a live volume.
* The setup Job re-runs after each upgrade and is idempotent: it only changes what drifted (for example, if you bump `store.wordpress.woocommerceVersion`).
* WordPress uses the `Recreate` strategy (single RWO volume), so the storefront has a short blip during its own upgrade; the gateway and dashboard do not.
* A changed LLM key or any gateway setting restarts the gateway automatically (config checksum annotation).
* Extra stores are separate Helm releases, one per namespace. A platform upgrade or rollback does not roll them back.

## Rollback

```bash
helm history mcp-portal
helm rollback mcp-portal <revision> --wait --timeout 10m
```

Rollback restores the manifests (images, config). It does **not** undo database changes: the store's MySQL and the gateway's Postgres data live on volumes and are untouched. For the gateway this is safe because migrations are additive. If a WooCommerce upgrade went wrong, restore the database backup as well. After a rollback, check that the LLM settings are still the ones you expect: rolling back to a revision that had none removes them.

To rehearse it: upgrade with a bad image tag (`--set image.tag=does-not-exist`), watch the new pod fail to pull while the old one keeps serving (`maxUnavailable: 0`), then `helm rollback` to the previous revision.

## Backups

State is the volumes plus the Secrets:

```bash
# MySQL (store)
kubectl -n store exec sts/mysql -- env MYSQL_PWD="$(kubectl -n store get secret mysql-credentials -o jsonpath='{.data.root-password}' | base64 -d)" \
  mysqldump -uroot --all-databases --single-transaction > store-$(date +%F).sql
# Gateway (users, keys, audit, servers)
kubectl -n platform exec sts/postgres -- pg_dump -U gateway gateway > gateway-$(date +%F).sql
# Uploads and plugins
kubectl -n store exec deploy/wordpress -- tar czf - -C /var/www/html wp-content > wp-content-$(date +%F).tgz
# Secrets (encryption key!) - store somewhere safe and separate
kubectl -n platform get secret gateway-secrets -o yaml > gateway-secrets.yaml
```

Losing `gateway-secrets` loses the ability to decrypt stored upstream credentials (you could re-enter them, but keep the backup). Extra stores keep their own data in their `store-<id>` namespace and are deleted with it; they have no built-in backup.

## Observability

* Gateway `/metrics` (cluster-internal only): `gateway_tool_calls_total{server,tool,outcome,via}`, `gateway_tool_call_duration_seconds`, `gateway_upstream_up{server}`, `gateway_auth_failures_total{reason}`, `gateway_chat_runs_total`.
* Structured JSON logs; each request line carries a request id that also appears on the audit row. `Authorization` and cookie headers are redacted.
* The dashboard shows live upstream status, **why** a server is unreachable, and latency. The chat assistant can also diagnose the platform through the kube-ops server ("why is currency-mcp unhealthy").

## Troubleshooting

| Symptom | Look at |
|---|---|
| `helm install` times out | `make status`; `kubectl -n store describe pod -l app.kubernetes.io/name=wordpress` (image pull? volume?) |
| Setup Job fails | `kubectl -n store logs job/wordpress-setup`. Usually outbound access to wordpress.org (check `networkPolicy.internetEgress` and your firewall). The Job is safe to re-run: `helm upgrade ...` again |
| WordPress pod crash-loops with permission errors | The pod needs `CHOWN, DAC_OVERRIDE, FOWNER, SETGID, SETUID, NET_BIND_SERVICE`; check your cluster's Pod Security or admission policy isn't stricter than `baseline` for the `store` namespace |
| woo tools say "authentication failed" | The REST key row was not written: re-run the setup Job and read its log |
| Server shows *Unreachable* | The dashboard shows the reason (DNS, refused, timeout, 401, rejected URL). For in-cluster hosts check `UPSTREAM_PRIVATE_ALLOWLIST` and the NetworkPolicy |
| Chat says "The assistant isn't configured yet" | `platform.gateway.llm.apiKey` is empty. It was probably dropped by a `helm upgrade` that did not include your values file |
| Chat says "The language model rejected the configured API key" | The key does not match `llm.baseUrl` and `llm.model` (a Gemini key needs the Gemini endpoint). Fix the three together in your values file and redeploy |
| `kubectl run` in `platform` is refused | That namespace enforces the `restricted` Pod Security level. Run test pods from another namespace, using the full service name (`malicious-test.platform.svc.cluster.local`) |
| Creating a store stays *Provisioning* | `kubectl get ns -l mcp-portal.io/store=true`, then `kubectl -n store-<id> get pods`. Usually memory: each store requests about 1 GB. It becomes *Failed* with a reason after `platform.stores.provisionTimeoutSeconds` |
| Cannot reach `*.localtest.me` | Your resolver blocks rebinding to 127.0.0.1: add the two hosts to your hosts file |
